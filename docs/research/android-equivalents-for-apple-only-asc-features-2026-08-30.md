# Android equivalents for Apple-only ASC features

Date: 2026-08-30

## Classification

- **Close equivalent**: Android or Google provides substantially the same developer outcome.
- **Partial analogue**: the capability overlaps, but its lifecycle, scope, or automation surface differs materially.
- **No direct equivalent**: no current supported Android/Google Play facility represents the same resource.

## Mapping

| Apple capability | Android/Google counterpart | Fit | What Gplay should do |
|---|---|---|---|
| App Clips | Google Play Instant was the historical counterpart, but Google ended Play publication and serving of Instant Apps in December 2025. Android App Links can route an installed user into a specific journey, and Play Feature Delivery can download a feature after the base app is installed. Neither provides a current no-install mini-app. [Play Instant retirement](https://developer.android.com/topic/google-play-instant/overview), [Android App Links](https://developer.android.com/training/app-links/about), [on-demand feature delivery](https://developer.android.com/guide/playcore/feature-delivery/on-demand) | **No current direct equivalent**; App Links and feature delivery are partial UX alternatives | Do not add an `app-clips` publishing family. A useful offline feature would inspect an AAB for dynamic-feature delivery and validate App Links/`assetlinks.json`; it must not claim to publish an instant experience. |
| TestFlight distribution and tester feedback | Google Play internal, closed, and open test tracks are the Play-native distribution counterpart. Open and closed testers can leave private feedback, but Google directs developers to view it in Play Console; the Developer Reply to Reviews API is explicitly limited to production feedback. Firebase App Distribution is the closer fully programmable analogue: its official REST API uploads binaries, manages releases, distributions, testers and groups, and can list/get/delete release-specific feedback reports containing text and screenshot links. [Play testing and private feedback](https://support.google.com/googleplay/android-developer/answer/9845334), [production-only Reviews API boundary](https://developers.google.com/android-publisher/reply-to-reviews), [Firebase App Distribution REST API](https://firebase.google.com/docs/reference/app-distribution/rest), [feedback reports resource](https://firebase.google.com/docs/reference/app-distribution/rest/v1/projects.apps.releases.feedbackReports) | **Close equivalent through Firebase App Distribution**; **partial inside Google Play alone** | Keep Play tracks/testers for store testing. Add an opt-in Firebase App Distribution provider for upload, releases, distribution, tester/group management, and feedback reports. Use its separate `cloud-platform` OAuth/IAM model and label it as Firebase—not as a Play Developer API feature. |
| StoreKit catalog, transaction, and server operations | Google Play Billing is the app-side purchase system. The Google Play Developer API manages one-time products, subscriptions, base plans, offers, purchases, acknowledgements, consumption, cancellation, deferral, revocation, refunds, and voided purchases. License testers and Play Billing Lab cover accelerated and failure-state testing. [Play Billing overview](https://developer.android.com/google/play/billing), [Android Publisher API catalog](https://developers.google.com/android-publisher/api-ref/rest), [billing test facilities](https://developer.android.com/google/play/billing/test) | **Close functional equivalent** | Continue evolving the existing monetization, orders, and purchases families rather than adding a `storekit` name. Remaining work should be API coverage and transaction correctness, plus local guidance for license testers and Play Billing Lab. |
| Xcode | Android Studio plus Gradle, the Android Gradle Plugin, Android SDK build tools, and `bundletool` provide build, test, package, and signing workflows. They are designed for command-line and custom CI use. [Android build system](https://developer.android.com/build), [command-line app-bundle tooling](https://developer.android.com/guide/app-bundle/test), [command-line tests](https://developer.android.com/studio/test/command-line) | **Close toolchain equivalent**, not a shared project format | Keep local Gradle build/test/sign/package helpers. Invoke the project's Gradle wrapper and official tools; do not attempt to own or reinterpret the Android build graph. |
| Xcode Cloud | Google has composable pieces rather than one Play-hosted build service: Gradle builds, build-managed virtual or Firebase Test Lab devices, and Firebase App Distribution. These can run in a developer-selected CI system, but they do not form a single first-party service with Xcode Cloud's lifecycle. [build-managed devices and Test Lab devices](https://developer.android.com/studio/test/managed-devices), [Firebase App Distribution Gradle integration](https://firebase.google.com/docs/app-distribution/android/distribute-gradle) | **Partial analogue** | Provide deterministic workflow recipes/adapters for build, test, upload, and release. Do not build a hosted CI service or present Play Console as one. |
| Apple certificates and provisioning profiles | Android requires APKs to be signed. For Play App Signing, developers retain an upload key while Google protects the app-signing key and signs distributed APKs. Android has no provisioning-profile or per-device registration layer for ordinary Play distribution. Standard Google-managed enrollment and upload-key reset remain Play Console flows; the official App Signing API is explicitly restricted to enterprise self-hosted Cloud KMS keys and warns against using it for standard enrollment. [Android and Play app signing](https://developer.android.com/studio/publish/app-signing), [enterprise App Signing API boundary](https://developers.google.com/android-publisher/api-ref/rest/v3/appsigning/enrollApp), [`apksigner`](https://developer.android.com/tools/apksigner) | **Close signing equivalent**; **no provisioning-profile equivalent** | Support local keystore/upload-key generation, certificate fingerprints, artifact signing and verification. Keep enterprise KMS enrollment/rotation separately named and scope-gated; do not invent profiles or automate the ordinary console-only enrollment flow. |
| Merchant IDs | Google Pay issues a merchant ID through the Google Pay & Wallet Console as part of production access. This belongs to the Google Pay API for physical goods and services, not the Google Play Billing or Android Publisher resource model. [Google Pay production access and merchant ID](https://developers.google.com/pay/api/android/guides/test-and-deploy/publish-your-integration), [Google Play Billing scope](https://developer.android.com/google/play/billing) | **Close payment-domain equivalent**, outside Google Play publishing | Keep it out of core Play parity. If product scope expands, use a clearly separate Google Pay provider and preserve its approval/manual-review boundary. |
| Pass Type IDs | Google Wallet uses an issuer account/issuer ID plus pass class IDs and pass object IDs. The official Wallet REST API manages classes and objects for event tickets, loyalty cards, offers, generic passes, and other pass types. [Wallet classes and objects](https://developers.google.com/wallet/tickets/events/overview/how-classes-objects-work), [Google Wallet REST API](https://developers.google.com/wallet/reference/rest) | **Close Wallet-domain equivalent**, outside Google Play publishing | Treat this as a separate Google Wallet provider or separate CLI, not a missing Android Publisher command family. |
| Notarization | Android has no developer-invoked operation that notarizes an arbitrary binary and returns a ticket that can be stapled for offline distribution. Google Play reviews and analyzes Play submissions, Play Protect scans apps on devices—including apps obtained outside Play—and pre-launch reports test uploaded artifacts. Android developer verification separately links a verified developer, package name, and signing certificate; its public APIs can register package names/keys and check registration status. None is binary notarization. [Play Protect analysis](https://developers.google.com/android/play-protect/cloud-based-protections), [pre-launch reports](https://support.google.com/googleplay/android-developer/answer/9842757), [Android Developer Console registration API](https://developer.android.com/developer-verification/guides/developer-console-api), [Developer ID status API](https://developer.android.com/developer-verification/guides/check-registration-status) | **Partial security analogues**, **no direct notarization equivalent** | Keep offline artifact preflight/signature verification. Add official Android developer-verification registration/key/status operations if desired, under that exact name. Do not call Play Protect, pre-launch testing, or developer verification “notarization,” and do not promise a notarization ticket. |
| Routing coverage | Android navigation apps advertise supported actions and URI schemes through manifest intent filters such as `geo:`; verified App Links route owned web URLs into app content. Google Play exposes no equivalent routing-app geographic coverage document in the Android Publisher API. [common map intents](https://developer.android.com/guide/components/intents-common), [App Links](https://developer.android.com/training/app-links/about), [Android Publisher API resources](https://developers.google.com/android-publisher/api-ref/rest) | **No direct equivalent** | Do not add a routing-coverage upload command. An offline validator can inspect map/navigation intent filters, deep-link patterns, `assetlinks.json`, and certificate fingerprints, but geographic coverage remains app-owned data rather than Play listing metadata. |

## Recommended implementation order

1. **Firebase App Distribution provider**: this is the strongest missing ASC-inspired feature family with a complete official API. Cover binary upload; release get/list/update/delete; distribute; tester and group operations; feedback report list/get/delete; pagination; output formats; dry-run for mutations; and mocked contract tests.
2. **Android developer verification operations**: extend the existing status capability with official package/key registration and ownership-verification workflows. Keep required identity review and justification states explicit rather than trying to bypass them.
3. **Local Android validation**: deepen signing-certificate, App Links, map-intent, dynamic-feature, and Gradle/bundle inspection. These are deterministic and do not touch a developer account.
4. **Keep separate product boundaries**: Google Pay merchant onboarding and Google Wallet pass issuance are valid Google counterparts, but they are not Google Play Console parity. Add them only if Gplay deliberately becomes a broader Google app-commerce CLI.

## Bottom line

The Apple-only list should not be treated as one bucket. StoreKit and local Xcode work already have strong Android equivalents; Firebase App Distribution provides a real, official TestFlight-style API including tester feedback; signing has a strong Android model without provisioning profiles; Google Pay and Wallet have close counterparts outside Play; and App Clips, notarization tickets, and routing-coverage uploads have no current direct Android/Google Play equivalent.
